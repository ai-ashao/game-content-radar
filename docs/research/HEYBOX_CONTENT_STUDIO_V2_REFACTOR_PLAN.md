## 0. 本轮必须改变的七件事

| 旧方向 | 新决定 |
|---|---|
| 一个项目同时服务小黑盒、SEO、建站选品 | 只服务小黑盒编辑与运营；删除活动流程中的 Site Score、SEO 页面建议、建站候选 |
| `game-content-radar` 与游戏词雷达容易混淆 | 改为 `heybox-content-studio`，界面名“盒友编辑台”，命令名 `heybox-studio` |
| 今天抓到什么新闻，就围绕什么写 | 同时建立“时效事件池”和“常青选题池”；没大新闻也能组织有价值内容 |
| 折扣、新游、人物、细节等七类散着做 | 聚焦一个受众，收拢为“买得明白／经典再发现／作品背后”三条栏目 |
| 热度与评论越高越值得发 | 先检查读者价值、事实、原创贡献和讨论质量；热度只作辅助 |
| AI自动产两篇，改几句话即可发布 | 先形成研究资料包和具体观点，再生成待审初稿；不承诺AI稿的原创或激励资格 |
| 运行一次产生几个 Markdown 文件 | 网页里完成选题、补证、初稿、审核、排期、发布记录、定时口径复盘 |

**产品定位：为中文 PC／Steam 单机与精品游戏读者，生产有证据的选购建议、经典重发现和游戏设计故事。**

对外的读者承诺可概括为：**买得明白，玩得更懂。**

“盒友编辑台”是内部工具名称，不是强制给运营账号改名，也不暗示小黑盒官方出品。本文没有核查商标或所有同名项目的可用性；正式对外商业化前另行确认，不作为本地工具开发门槛。

## 1. 为什么是这个垂直，而不是泛游戏资讯号

### 1.1 对本人的适配逻辑

已知需求是：单人操作、希望AI半自动化、能读来源并审核、以网页为主、不希望每天人工从零写稿。现有代码能处理结构化信号与证据，因此优先发挥“数据筛选、材料整理、对照解释”的能力。

尚未确认的是：本人实际玩过哪些游戏、愿意投入多少实机录屏时间、是否熟悉某个系列。因此**不能把账户人设定义为“千小时魂系老玩家”或“通关百部3A的测评人”**，也不能默认本人愿意每天花数小时追新游。

账号初期更适合“有筛选标准的游戏编辑”，而不是伪造体验的职业评测者。

### 1.2 受众与范围

首期主受众：中文PC／Steam玩家，关注单机、可单人游玩的精品游戏与适度合作游戏；想知道值得买什么、旧游戏还有什么值得重看、某个设计为什么有意思。

可涵盖多个游戏，不必立即锁死单款游戏。但每条内容至少服务以下一个问题：

- 这款／这组游戏是否适合我，现在该怎么买、怎么选？
- 我认识的游戏，是否有值得重新理解或再次游玩的价值？
- 某个人或工作室做出的选择，如何体现在作品中？

默认不扩展到泛生活热点、明星私生活、擦边图帖、电竞战队争吵、虚构名人语录或纯公司财富攀比。与主题相关的主机历史可以写，但应明确平台，不把所有主机游戏说成Steam可买。

### 1.3 不再把导流作为选题必备条件

文章须在小黑盒内完整提供价值。自有站点链接不是栏目指标；不为塞入WorkshopFetch等站点链接而选择题目。未来确有工具相关主题，可由人判断是否附加实用资源，但不自动插入推广CTA。

## 2. 本次调查如何改变内容判断

本次观察不是全站统计：9组主题检索的首批89张卡片、公开首页补充、53条唯一代表样本，以及4篇正文与部分可见评论。数字是评论／点赞快照，不是浏览量。完整口径见配套调查报告。

| 方向 | 观察到的代表对照 | 针对本项目的判断 |
|---|---|---|
| 折扣／史低 | 大合集出现1,222、2,054点赞；同类新发帖也有96点赞 | 保留作轻内容，但从“更多款”转向人群明确的精选；不能承诺日更百款必有流量 |
| 评分／游戏筛选 | 明确门槛的筛选帖出现1,545、3,577点赞；某个人主观八维评分为13点赞 | 优先测试“数据口径+可执行筛选”，不自动生产主观神作榜 |
| 经典回顾 | “记忆中的游戏也在Steam”2,325点赞；泛经典推荐47点赞 | 经典题材要有今天仍有用的找回路径、版本比较或具体新问题 |
| 隐藏细节 | 大镖客细节520点赞；匹诺曹隐藏内容7点赞；星露谷某秘密摘要0点赞 | 标题标签不是价值本身；必须有一个可观察的细节和证据 |
| 新游介绍 | 同作者不同月份盘点50、138、359点赞；另有年度盘点810点赞 | 有选择地介绍，不做“所有新品都写”的商店文案翻译号 |
| 厂商排名 | 某营收榜1,911评论／922点赞；“对玩家最好”350评论／5点赞 | 榜单可以制造讨论，但不等于信任；做有限口径的专题，不做主栏目 |
| 宫崎英高等人物 | 赞誉文章226评论／31点赞；另有数千点赞的玩梗帖 | 人物是认知入口，不是万能流量词；核心应回到作品、采访和设计选择 |

**这些对照不控制曝光、账号规模、时间、活动与题材，不能据此算类型收益或给出因果排序。** 例如评分正文的部分热评是视觉小说玩梗，人物正文的部分评论是攻击其他制作人；都不能全部记作高质量讨论。

调查导出的产品策略是“优先测试”，而不是把这些数据直接作为训练标签。

## 3. 三条主栏目、七种内容形态

### 栏目一：买得明白

包含：精选折扣、评分筛选、新游前瞻。

**A. 精选折扣／购买决策**

读者收益：省去比价、筛游戏和辨认版本的时间。

优先结构：`限制条件 → 5–12个候选 → 为什么选它 → 不适合谁 → 价格／版本／截止时间`。5–12是本项目的初始编辑建议，不是平台要求。只有3款真值得说就写3款；大促确需20款以上时分组，不凑数。

不默认采用“所有折扣+百款大合集”；不用“我通关后认为”来包装资料整理。无历史价格证据时标题只用“折扣／本次清单最低X元”，不用“史低／全网最低”。

**B. 评分筛选／有口径的榜单**

读者收益：把数字变成适合自己的候选，不把高分当唯一标准。

可做：某品类、最低评价样本、中文支持、某价格区间、单人／合作条件的筛选；同款游戏近期与长期口碑差异；不同平台评分为何不一致的解释。

先使用可靠可取得的Steam数据。小黑盒评分与拥有量不在当前稳定采集能力中，不得因为研究样本有这些字段就宣称我们也已经拥有。无法稳定获取时人工录入有出处的少量数据，或者明确只做Steam口径。

**C. 新游前瞻／适合谁**

读者收益：三分钟明白一款游戏实际在玩什么，以及是否该列入关注。

要求一个真实差异：关键机制、玩法组合、短局／慢节奏场景、可信团队背景、Demo体验入口、明确适合或不适合的人群。没有玩过时定位为“资料前瞻／机制介绍”，不是“体验评测”。

标题可用真实玩法比较，不能把“像某游戏”改写成“该团队新作”。抽取商店广告语后需补边界或未知事项，不机械写“爽感拉满、闭眼入”。

### 栏目二：经典再发现

包含：经典新视角、细节与设计拆解。

**D. 经典回顾／旧作新问题**

不能只复述剧情和年份。选题需要一个问题，例如版本选择、重玩时理解改变、无导航设计、地图结构、叙事手法、童年作品的现代入口。

文章允许是有依据的解释，但必须用具体场景支撑；作者没重玩就不能声称“我重玩20小时才发现”。价格、商店上架、补丁状态仍须更新核验；游戏史料旧不代表选题过期。

**E. 隐藏细节／一个细节解释一种设计**

把“你可能没注意”转成可展示内容：`在哪里 → 什么条件 → 画面／动作证据 → 为什么有意思 → 解释有哪些边界`。

如果只有某篇文章声称存在该细节，没有画面、原始视频时间点或可复现材料，进入待补证，不进入可发布队列。将玩法可观察事实与“开发者有意这样做”区分；后者需要开发访谈或其他直接依据。

允许用已知细节提出新的分析，不必制造“首次发现”。剧情重度内容必须加剧透分级，标题与封面不泄露关键结局。

### 栏目三：作品背后

包含：制作人／工作室故事、有明确口径的作品或厂商专题。

**F. 制作人与开发故事**

以“一个决定+作品后果”为单位，而非百科履历流水账。

宫崎英高、小岛秀夫等熟悉的人物，可以作为读者入口；稿件核心应是一次采访、开发限制、方向选择或作品设计。不据他人转述替当事人心理下结论，不把旧采访包装成刚刚表态。

人物没有直接制作所有相关作品：每篇必须核对该作品的具体职务与贡献范围。作品由团队完成，不把公司/团队全部成果自动归给单个人。

**G. 厂商／开发者／作品排名专题**

降为低频实验，不做每日主线。首先分清排名对象：人、开发工作室、发行商、集团、某一系列作品。

可做“限定时期的已发售作品口碑”“按官方奖项统计的作品回顾”等；必须公开纳入条件、样本量、版本去重与统计日期。不能把营收／市值当作游戏品质，不用伪客观“全球游戏开发者实力榜”。

如果是个人偏好，明确主观标准且由真实玩过的人提供偏好资料，AI不能冒充用户创建私人品味。

## 4. 初始栏目组合与现实投入

默认以 **40%买得明白、40%经典再发现、20%作品背后** 作为一个月的试验配比，不作为每日硬性任务，也不是平台算法最优值。

日目标仍可设为最多两篇，但改为：**一篇完成核验的轻内容，加零至一篇已经研究完成的常青稿。** 没有成熟第二篇就不发，不临时让模型硬编一个。

第一阶段不追求全七类同时高频上线：优先跑“精选折扣／评分筛选”与“经典重发现”两个稳定流程，再补细节复现、人物深稿。首次组建资料库可能比后续日常编辑花时更多，不能承诺每篇都只需2分钟人工。

重型稿件（实机验证、长采访对照、复杂排名）每周先安排不超过2篇，其余常青稿可以是较小的单问题拆解。每篇记录实际人工分钟数；用户可在设置中定义日/周预算，超预算选题保留在排期池，不因为分高就自动挤进今天。

建议首月以形成 **两条可信、能持续产出的栏目** 为成功条件，而不是完成60篇模板稿。

## 5. 项目改名与职责边界

### 5.1 统一命名

| 层级 | 新名称 |
|---|---|
| 推荐仓库 | `heybox-content-studio` |
| 产品显示名 | `盒友编辑台` |

| Python分发包 | `heybox-content-studio` |
| Python导入包 | `heybox_content_studio` |
| CLI | `heybox-studio` |
| 界面主动作 | `更新选题池`、`生成选题简报`、`生成待审稿` |
| 对外定位 | PC／Steam单机与精品游戏选购、重发现、设计故事 |

**不要继续注册 `game-radar` 作为该项目的默认可执行文件。** `game-keyword-radar` 已经使用同名入口，在同一环境安装会产生混淆。开发启动器使用本项目虚拟环境的 Python 模块入口，尽量不依赖系统PATH。

仓库重命名由操作者在确认后执行；本计划不执行远程变更。旧目录、PID与数据需要显式迁移，不能简单搜索替换后丢失历史内容。

### 5.2 彻底分离

`heybox-content-studio` 不计算新站价值、不产生SEO页面图谱、不查关键词KD、不运行跨平台需求增长引擎。相关功能属于 `game-keyword-radar`。

两项目不互相import源码、不共享可写数据库、不以另一个服务在线作为运行前提。偶尔需要借用公开信号，使用人工选择的轻量JSON/链接导入即可；该交换不是V2完成前提。

Steam在线人数可作为某条已选新闻的背景资料，但不在本项目维持完整“Steam+Twitch+Trends增长评分”。已有玩家快照归档保留，未来迁移由游戏词雷达单独处理。

## 7. 新工作流：双选题池，不再只有每日事件

```text
时效池：折扣／限免／新游／更新／口碑变化
                            \
                             → 选题候选 → 栏目与受众匹配
                            /                ↓
常青池：经典作品／机制／细节／开发故事      选题简报 EditorialBrief
                                             ↓
                                    研究资料包 SourcePack
                                             ↓
                                主张核验 + 原创贡献 + 素材确认
                                             ↓
                                        AI待审初稿
                                             ↓
                                  人工审核／修改／排期
                                             ↓
                                       小黑盒手动发布
                                             ↓
                               24h／72h／7d数据与人工时间记录
```

默认“更新选题池”只更新候选与轻简报，不立即消耗模型调用为所有候选写全文。用户选择一个具体角度后才做深研究与初稿。

有资料且通过检查的常青题可以跨日保留，不因源文章超过72小时而淘汰。时效池按事件时间和截止时间判断；常青池按解释价值、资料有效性与近30天是否写过同一角度判断。

### 每天的实际操作

打开编辑台后查看今天建议的轻内容，以及常青池里已备齐资料的候选。点进简报，先看到结论、来源与缺口，而不是先看到800字成稿。补齐必要事项或换题，再生成初稿、核对图文并发布。发布后贴入帖子链接，之后按统一时间窗录入后台能看到的数据。

AI可以整理、计算、生成草稿；“人工审核”并不要求人从空白页写文章，但也不能退化成只看标题改语气。

## 8. 选题简报比文章模板更重要

每个 `EditorialBrief` 必須回答：

1. 给谁看？属于哪条主栏目？
2. 只解决哪一个问题？一句话结论是什么？
3. 与已有同题相比，新增的是数据、比较、重现还是解释？
4. 哪些是可核验事实，哪些是编辑判断，哪些仍待查？
5. 需要哪些图片／视频时间点／表格来证明，而不是只装饰？
6. 预计审核成本、截止时间、剧透程度分别是什么？

示意数据（全部是结构示例，不是已验证稿件）：

```json
{
  "brief_id": "brief-demo-001",
  "column": "classic_rediscovery",
  "content_form": "single_question_analysis",
  "audience": "熟悉某经典作品、但不想重读剧情梗概的PC玩家",
  "subject_ids": ["game-example"],
  "reader_question": "这个游戏怎样在不打断操作的情况下引导玩家？",
  "angle": "比较三个具体场景中的视觉引导手段",
  "thesis": null,
  "evidence_status": "needs_research",
  "required_claim_ids": [],
  "original_contribution": null,
  "missing_evidence": ["三个场景的画面与触发条件"],
  "spoiler_level": "mechanics_only",
  "freshness_mode": "evergreen",
  "estimated_human_minutes": null,
  "status": "backlog"
}
```

“换个标题、换同义词、按原文逐段改写”不算新增价值。“重新定义样本+程序筛选+解释限制”可以形成编辑贡献；“自己复现并对照两张图”也是贡献。贡献应在内部简报里记录，不等于平台一定认可原创资格。

## 9. 数据源职责与可用性

来源分成两种，必须分开标记：

- **发现来源**：告诉我们有人在讨论，不直接证明讨论内容是真的。
- **事实来源**：支持稿件某一个明确主张。

| 来源 | 用途 | V2接入方式与边界 |
|---|---|---|
| 小黑盒公开首页/检索/作者页 | 校准角度、寻找玩家问题、观察格式 | 现有静态HTML适配器不保证有内容。默认支持人工贴链接/标题/截图；可选渲染页面导入，先验证权限与稳定性，不承诺全站爬取 |
| Steam商店 | 当前价格、版本、语言、描述、游戏图片 | 复用现有公开数据路径；逐字段保存地区/时刻/商品ID。首页列表只是候选集，不宣称扫描了全Steam |
| Steam评论接口 | 明确口径的评价统计、正负面意见样本 | 新增独立适配器，按官方参数解释过滤范围。`review_score`不是0–10主观分；`total_reviews`是匹配查询条件的总数 [S1][S2] |
| 游戏/发行商官方公告 | 发售、更新、免费活动 | 复用RSS/Steam新闻；保留实际发布者，Steam新闻接口转发的媒体内容不自动算开发商原话 |
| 官方访谈、开发日志、开发者演讲 | 人物观点、设计意图、开发约束 | 研究资料包导入，记录作者/日期/段落或视频时间码；不是今天自动搜全网就一定能拿到 |
| 正式游戏画面、操作复现 | 隐藏细节、机制解释 | 用户截图/录屏，或可合法引用的原始演示；必须标明版本和来源 |
| 可靠媒体/公开档案/社区原帖 | 补背景、发现疑问 | 分类为二手/社区材料；重要引语追溯原始出处，不以转载数量替代独立证据 |
| 评分聚合站/财报/获奖记录 | 特定榜单 | 明确样本与平台；没有稳定数据即人工导入或不做该题，不绕付费墙或受限接口 |

### Steam评论的特别实现要求

官方接口为 `GET store.steampowered.com/appreviews/<appid>?json=1`。实现需保存 `language`、`review_type`、`purchase_type`、`filter_offtopic_activity`、抓取时刻等参数；分子分母来自同一口径。近期摘要与全时段统计不能混用。不得把API `day_range` 参数简单解释为可获得完整“最近30天官方好评率”；实现前应按该参数说明验证范围，不能用一页评论代替总体。[S1][S2]

默认先只为入选候选取轻量统计和有限正/负评价样本，不递归抓取所有评论，不保存不必要的用户个人信息。评分榜样本范围必须写在文章里，例如“本次候选池内”，而不是未经全库扫描就写“Steam全部游戏前十”。

### 失败和免费边界

来源状态至少含：`ok / partial / empty / not_configured / needs_access / rate_limited / failed`。缺少数据不是零分/零需求。付费搜索或AI API不是强依赖；可保留现有模型适配器，也要支持导出资料包到用户自行使用的网页AI。程序不得自动登录、操作第三方网页AI批量生成/发布。

对需要Key/权限的能力，只展示未配置与指引，不伪装已实现无门槛接入。单源失败保留其他结果；关键事实来源失败则相应稿件停留在待补证，而非随便换一个社区帖子当真相。

## 10. 七类事实与内容校验

### 10.1 价格校验

保存 `store / region / currency / app_or_sub_id / edition / observed_at / end_at / current_price / historical_low_evidence`。

同款不同版本、Steam直购、CDK、平台券后价分开；人民币与美元分开。相同折扣百分比不保证相同历史价格。历史低价证据缺失即去除“史低”用词；不能通过改写为“最低价”继续暗示历史最低。数量与最低价根据最终选入清单计算，不从原始条数抄。

发布前重新检查时效价格与截止时间；默认30分钟内核验作为本地流程参数，可配置，**不是平台规则**。限时免费试玩不能写成永久入库。

### 10.2 评分与排名校验

区分Steam推荐百分比、小黑盒十分制、媒体评分与用户评分，不能直接求平均。每条显示口径、样本量、平台、版本、统计截止时间。评分人数不足时提示，不把零评论游戏评为0分。

“95%好评”必须存在同口径分子分母。自定义排行公开入围范围、最低样本、排序规则、同名/重制/DLC去重方式；收入榜还需财政年度、币种和实际/估计性质。不要自动生成“人类公认最强”结论。

### 10.3 作品职务与归属校验

人名、工作室、发行商、集团分别建实体；同一人可在不同作品担当不同角色。宫崎英高“参与/监督/总监”等表述以具体作品可信credit为准，不能由系列品牌关系推断全权设计。人物故事围绕作品与已公开工作，不扩展到私生活猜测。

### 10.4 引语与历史时间校验

关键引语必须有原始页/视频、具体段落或时间码、原始发布日期。直引、译文与概述分别标记。旧采访允许重新分析，但正文写明历史时间；不得根据文章近期重新出现就说“最新采访”。没有原始引语时可描述“某报道转述”，但不能把未经核验的强说法放在标题。

### 10.5 细节复现与解释校验

观察事实提供 `platform / build_or_version / prerequisites / reproduction_steps / visual_evidence`。可用画面确认，不必强制作者通关整部游戏；仍不可把外部演示说成自己亲测。

“机制可能造成某体验”是编辑推论；“开发者故意这样做”需要更强来源。禁止未经证据的“所有NPC／首次发现／99%玩家不知道”。

### 10.6 原创贡献与AI边界

保留AI辅助，但不用AI检测分数评价稿件，也不做改写避检。原始素材中的指令一律视作不可信文本，不允许驱动工具执行、修改规则或泄露本地Key。

每篇记录 `original_contribution`、模型辅助范围与人工检查人/时间。AI不能凭空添加自己的经历、喜恶评分、神秘内幕、采访对话或游戏小时数。草稿里语气自然不等于事实正确，也不等于平台认可原创。

### 10.7 剧透与素材校验

素材记录来源URL、本地文件、作者/发布方、用途、时间码、引用/使用条件。优先官方素材与自己的截图，不从别人的合集整套复制；不知道授权就标为待确认。不要用AI生成图伪造游戏证据。

支持 `none / mechanics / minor_story / major_story`；重剧透在生成标题与封面前先提示。图片数量由解释任务决定，不设“必须8张”的形式门槛；每张应有明确说明作用。

## 11. 平台规则：撤回过于乐观的旧前提

之前仅凭未查到禁止条款，推断“AI整理后稍作修改就可放心运营/获激励”并不充分。新计划明确：**未看到禁止不等于平台承诺接受。**

本次在原站读取了社区管家的2025-12-26周报，明确可见广告引流、引战、低俗内容与异常行为治理；另发现2025-09-07周报的历史转刊，提及频繁用AI/固定模板发帖的识别及激励资格风险。9月7日原站搜索卡片可定位，但详情正文未成功读取，因此AI相关段落仍按历史转刊证据记录。[P1][P2][P3]

不能从这些资料推断“2026年所有AI辅助都被禁”，也不能反向保证AI初稿一定符合现在公约。V2因此加入 `PolicyReview`：原规则入口、检查日期、AI说明要求、激励适用性、人工备注。没有核验现行激励要求，就显示“资格未确认”，不显示“预计奖励”。

`500–1500字`之类可作为本地编辑建议，不能在未重新读取当前计划时声称是现行官方门槛。项目第一版不做激励收益估计，也不承诺平台不会限流。

## 12. 编辑优先级：先准入，再分栏目排序

### 12.1 准入检查

进入“可生成初稿”必须：主题属于受众范围；有明确读者问题；核心事实有可读来源；不存在无法处理的引语/价格/人物角色错误；有至少一个具体新增价值方向。

进入“待发布”还必须：必要证据和素材通过人工核对、剧透标记正确、时效事实未过期、已记录实际原创贡献。模型只能给出校验建议，不能自动代替人工批准。

材料不足但有价值的选题留在 `needs_research`，不是简单删除；不合受众的题标 `out_of_scope`，即使它点赞很高也不推荐。

### 12.2 初始优先级权重

以下为设计初值，不是从53条样本拟合的公式：

| 维度 | 权重 | 必须给出的理由 |
|---|---:|---|
| 读者收益 | 25 | 具体减少什么决策成本或提供什么新理解 |
| 角度与新增贡献 | 20 | 相比原始材料新增什么，不是换句话说 |
| 证据与素材准备度 | 20 | 关键claim覆盖、可核对程度 |
| 受众/系列适配 | 15 | 为什么适合本账号而非泛热点 |
| 制作可行性 | 10 | 剩余人工步骤、预计成本、可复用资料 |
| 发布时机 | 10 | 截止时间/新版本/周年，或常青题的当前排期价值 |

每维只能在有输入依据时评分；未知写 `unknown` 并降低准备度，不凭模型补数。显示总分时命名为**编辑优先级**，不命名“爆款概率”。材料置信度独立显示。

时效题的发布时机来自事件与截止时间；常青题不按资料年龄机械扣分。两种池分开排序，再按栏目配比组合，不让低价集合因覆盖游戏多而永远压过经典稿。

评论/点赞可以帮助发现对照，但不直接进入权重。若后续拥有本人数据，可在相同栏目、相近曝光时长条件下调整，不把别人大号的累计点赞当自己的预期。

## 13. 标题与正文：模板是骨架，不是量产机器

### 13.1 标题工作方式

每个已通过基本核验的简报生成3–5个候选。分别尝试读者利益、具体问题、信息反差、熟悉作品锚点，避免所有标题同句式。所有数字都来自最终稿的结构化事实。

候选标题不显示“AI预测点击率93%”；可以标“主张已核对／缺历史价格／标题含剧透”。选择原则是信息清楚且正文能兑现，不是感叹号更多。

### 13.2 可用形态（均为待研究的角度示例）

| 形态 | 标题结构示例 | 核心材料 |
|---|---|---|
| 价格+场景 | `预算{X}元，想找单人游戏？这{N}款先看这几个区别` | 最终清单价格、单人支持、玩法差异 |
| 评分筛选 | `高分不等于适合所有人：这份{类型}清单先看筛选标准` | 可复算样本与边界 |
| 经典再发现 | `那些小时候玩过的{类型}游戏，现在该找哪个版本？` | 原作/移植/重制区分、当前入口 |
| 设计解释 | `不靠箭头提示，这段流程怎样让玩家知道往哪走？` | 实际场景与对照证据 |
| 一个细节 | `《{游戏}》这个不起眼的反应，为什么让世界更像真的？` | 条件、画面、解释边界 |
| 新游资料前瞻 | `喜欢{玩法}的人可以留意：{游戏}真正不同的是这一点` | 已确认机制、未知事项、Demo状态 |
| 人物与作品 | `从一段旧访谈，看{制作人}如何取舍{某个设计问题}` | 原访谈日期、原文与作品例子 |
| 有界榜单 | `只统计{范围}的{指标}：这份{工作室/作品}清单怎么排？` | 数据集、范围、排序算法、统计时间 |

禁止无证据的“首次／史低／神作／全部／官方证实／99%不知道”。对“神作”可以作为明确主观引语讨论，但不能让系统替用户制造这样的体验判断。

### 13.3 正文长度建议

轻资讯或限免信息可以短；精选清单和中型解释通常需要更多篇幅。默认编辑建议为轻稿约300–600字、主稿约700–1300字、复杂专题按证据扩展。这些不是平台规则，也不为达字数加空话。

每篇先回答一个问题，再呈现材料、判断与限制。互动问题可选：没有自然问题就不硬加；不要以争吵、辱骂、虚假投票诱导评论。

## 14. 数据模型与存储契约

新增模型均为计划，不代表已实现：

| 模型 | 最少字段 |
|---|---|
| `Subject` | subject_id、game/person/studio/publisher类型、名称/别名、平台ID、确认状态 |
| `EditorialBrief` | 栏目、人群、问题、角度、thesis、关联subject、原创贡献、成本、时效、剧透、状态 |
| `SourceRecord` | URL、来源类型、发布者、原始日期、读取时间、读取结果、摘要/必要摘录、访问限制 |
| `Claim` | claim_id、主张、fact/inference/opinion/quote、来源定位、核验状态、有效期、冲突来源 |
| `MediaAsset` | asset_id、来源/本地路径、用途、caption、时间码、使用条件、剧透级别 |
| `DraftRevision` | brief_id、revision、标题候选、正文、claim引用、模型辅助、人工修改、创建时间 |
| `PublicationRecord` | brief_id、发布平台、实际帖子ID/链接、发布日期、采用稿件版本 |
| `MetricSnapshot` | post_id、observed_at、post_age_hours、views/likes/comments/favorites/shares/follows、统计来源、空值原因 |
| `PolicyReview` | 规则入口、核验日期、适用说明、激励资格状态、人工备注 |

状态流：

```text
backlog → needs_research → brief_ready → draft_ready → in_review
        → approved → scheduled → published
```

分支状态：`out_of_scope / blocked / expired / archived`。后台自动处理最多推进到 `draft_ready`；`approved`及之后由用户触发。

目录建议：

```text
data/editorial/
  subjects/
  briefs/
  source-packs/
  claims/
  assets/
  drafts/{brief_id}/{revision}/
  publications/
  metrics/
  policy-reviews/
reports/{mode}/{run_id}/
legacy/manifest.json
```

继续本地文件存储即可，不增加云数据库。文件原子写入，编辑版本不可静默覆盖，模式和run_id隔离。`latest`按模式维护；示例模式不会覆盖真实报告，离线空测试不会清除待发布稿。旧数据兼容读取，不因为改名改写所有历史事实。

## 15. 网页信息架构

主页不再出现“Site(pre)／SEO Opportunities／最佳建站候选”。推荐结构：

```text
顶部：盒友编辑台 | 服务状态 | 数据更新时间
主动作：更新选题池

今天可处理什么？
  轻内容：一篇证据齐的选购/资讯稿
  主栏目：一篇准备成熟的常青稿
  每张卡：读者问题、栏目、证据状态、剩余步骤、预计人工时间

选题池：时效 / 常青 / 待补证 / 已排期
研究资料：事实、分歧、来源、截图、采访位置
编辑工作台：标题 / 正文 / 原创贡献 / 事实核对 / 素材
发布记录：手动贴帖子链接，记录采用版本
数据复盘：24h / 72h / 7d + 人工成本
设置：栏目、题材池、来源、模型、预算、规则检查
```

默认只显示中文日常术语。测试模式、文件路径、原始JSON放高级设置。首次空状态必须说明“还没运行”，不能显示成“所有来源零需求”。无报告、来源失败、本地后端断开是不同状态。

后端断开时状态点与文字同时变化，显示如何重启；重连后保留当前编辑草稿。浏览器可以复查本地缓存，但须标缓存及时间，不假装服务在线。不能声称已保存而实际只保存在未持久化页面内存。

### 编辑器的核心改变

左侧写作，右侧对应事实与素材；点某个数字/引语能回查来源。存在关键缺口时提示具体项，不只显示一个模糊“可信度低”。标题或数字人工改动后，应将受影响的核验标记置为待复查，而不是沿用旧版本已通过状态。

保留一键复制，但复制不是自动发布。用户可以导出“完整稿+素材清单+核验提示”供自己操作小黑盒。

---

## 16. 无额外模型API费用的半自动路径

保留现有Codex或外部模型适配器；不绑定新付费服务。另提供“导出写作资料包”，将已经选定的角度、事实、来源摘要、反例、约束与输出格式交给用户自行在网页AI中使用，再导入初稿。

资料包不只导出URL：无法读取的URL应提示，不能假设网页AI一定能访问。必要来源材料经过人工确认后附上摘要或允许引用的短片段；不整篇拷贝他人付费/版权文章。

默认提示词要写清：只用已提供和已核验材料；没有证据就标缺口；不要添加第一人称经历；不要生成未经核实的评分/价格/名言；将解释与事实分开；返回待审稿，不自称已经核验成功。

API调用失败时降级为“资料简报/待写大纲”，不能用几段空泛模板顶替“完成稿”，也不能自动切换到未经用户允许的收费服务。

## 17. 发布后的学习：用自己的数据，不拿对照样本当答案

### 指标

主要看：可用选题占比、核验一次通过率、实际人工分钟数、需纠正事实数、是否形成持续栏目。发布表现按可获得数据记录点赞、评论、收藏、阅读和关注；缺失即 `null`，不能补0。

统一在发布后24h、72h、7d记录；无法精确准点时写实际小时数。没有阅读量就不计算互动率/点击率。没有单帖涨粉归因就不把当天净涨粉分给某篇。

抽样检查评论质量：补充经验、提问、纠错、玩梗、争吵分别备注；不自动将所有回复算正反馈。样本有限时先做人工周复盘，不训练“爆款模型”。

### 四周试验

第一周建立最小题材池与两个主流程；第二周观察不同角度，逐渐稳定发稿；第三周在同栏目中小幅改变标题或选材；第四周根据本人数据保留2–3个有反馈、成本可控的栏目。

这不是严格随机A/B测试。不要同一天重复发同内容的两个标题来测试；不要在不同帖子年龄、活动奖励和大号基数下直接比累计点赞。

没有足够同类样本时结论显示“继续观察”；30篇可以触发一次复盘，但不能写成有统计保证的学习门槛。禁止因为两篇低表现就用更刺激的名人争议填补。

## 18. 工程实施路径

### M0：改名、边界与无损迁移

目标：用户能清楚区分两个产品，现有功能不丢。

更新pyproject/导入/README/网页标题/脚本；独立命令与服务标识；移除新运行的SEO分支和UI；停止默认CCU增长研究。读取旧版报告与编辑稿并生成迁移清单；数据先备份，禁止删历史目录。`game-keyword-radar`不做本次修改。

验收：两个虚拟环境能各自启动；旧报告可下载；新网页没有Site/建站排行；后台服务正常退出启动脚本仍可访问；启停脚本只处理本项目实例而非按端口误杀。

### M1：栏目、双选题池与研究简报

新增Subject/Brief/SourcePack/Claim数据契约；时效和常青池；来源状态；准入检查和按栏目排序；取消硬凑两篇。加入人工链接/资料导入。

验收：当天无新闻仍可选中有材料的经典题；重复同角度不会每天再造一篇；全不合格时不给虚假推荐。

### M2：选购与评分可复算流程

复用价格采集，新增Steam评论统计适配器与请求预算；精选清单按地区/SKU/口径计算；价格与评分校验。小黑盒评分先走人工核验输入，不阻塞核心。

验收：清单数量与标题一致；史低缺证不能使用；近期/长期/不同语言评论不能混算；可输出一份能人工核对的购买资料简报。

### M3：经典、细节与作品背后的研究包

新增经典角度、截图/视频定位、采访时间与人物作品credit、观点/事实分离、剧透提示。AI写作输入改用简报而不是原始新闻条目。

验收：一份经典稿和一份人物/细节稿能逐条找到论据；不编用户经历；材料不足留在待补证；不宣称模型校验等于人工事实核查。

### M4：完整编辑与发布记录

完成资料与正文对照编辑器、版本化保存、审核状态、简单排期、复制/导出、手动发布链接与指标录入。不要开发自动发布或自动互动。

验收：用户在网页完成“选题→补证→初稿→审核→记录发布”，刷新/重连不丢编辑；示例数据不能污染真实稿库。

### M5：真实试用验收与文档回写

至少试做选购、经典、作品背后三个方向的真实资料包；不是必须公开发布。记录获取失败、人工补充与耗时。跑第一批实际发布数据再调整权重；同步功能清单，将“已实现”“仅接口预留”“人工输入”“未验证”分开。

不做全网知识图谱、不做账户系统、不做多账号矩阵、不做云SaaS、不做自动发文机器人。这些不是该版本的完成条件。

## 19. 必须加入的验收用例

1. 未联网时显示未联网，不能生成“今天真实热点”标签。
2. 示例与真实记录分别保存；示例运行不覆盖真实latest。
3. 旧版编辑稿、报告和玩家历史能在迁移清单中定位，无静默删除。
4. 无合格题时推荐为空，不能fallback到最高但不合格的一项。
5. 常青资料超过72h仍可入池，时效折扣过期则不可进入待发布。
6. 一个来源失败只影响对应证据，整体网页仍可用。
7. 某真实受众无关的高评论梗帖不能因热度成为推荐。
8. 游戏数量、百分比、最低当前价由代码从最终清单计算。
9. 没有同商品/同地区历史价格证据时，所有标题候选不含史低暗示。
10. 限时试玩、领取保留、F2P三者不混淆。
11. Steam推荐率与其他平台评分分别存储；无评价不写0分。
12. 评分接口过滤参数写入数据；不能用一页评论声称全体玩家评价。
13. 数据列表只覆盖候选池时，标题不能声称全Steam/全行业排名。
14. 制作人、开发商、发行商分开，旧任职材料不能自动补成现任职位。
15. 转述语句、译文和直接引语分开；没有原始出处不生成强引语标题。
16. 无作者实测记录时，稿件不能出现“我玩了XX小时/我亲测”。
17. 细节演示有平台/版本/条件或原视频时间码；解读与设计意图分开。
18. 重剧透内容提示；封面和标题不泄露关键剧情。
19. 非可信来源内容中的指令不会改变系统规则或执行本地命令。
20. 人工修改已审核数字后，该事实重新变为待核验。
21. 模型不可用时输出研究简报，不冒充完成了一篇合格文章。
22. 没核实当期规则时，不显示“AI稿符合激励”“预计收入”等承诺。
23. 无浏览量不计算点击/互动率；暂无单帖关注数据不杜撰涨粉归因。
24. 草稿版本化保存、断线重连、复制及导出可以在真实浏览器验收。
25. 启动后终端关闭服务仍在；健康检查断开时文字/颜色一致。
26. `heybox-studio` 与关键词项目的 `game-radar` 互不覆盖；本项目数据路径独立。

自动测试覆盖模型和计算，浏览器测试覆盖工作流，真实来源测试覆盖采集质量。三者分别报告，不能只做语法检查就宣称完整验收通过。

## 20. 第一批“待研究”题目，不是假成稿

下列仅为角度种子，所有带事实暗示的部分必须先核验。不得原样当作“已发生的今天新闻”。

| 主栏目 | 选题角度 | 完成前需要什么 |
|---|---|---|
| 买得明白 | 本周折扣中，适合一个人慢慢玩的5款游戏 | 当期价格、单人支持、玩法理由与不适合条件 |
| 买得明白 | 同样高好评率，100条评价和10万条评价该怎么理解 | 统计口径与例子；避免把样本量机械等同质量 |
| 买得明白 | 买本体还是合集：某经典系列现在的版本怎么选 | 各SKU内容、地区售价、重复购买提醒 |
| 买得明白 | 一款新游到底像谁：先拆机制，再看宣传比喻 | 官方玩法与演示、明确相似维度、未知事项 |
| 经典再发现 | 小时候玩过的小游戏，现在能找到哪些正式版本 | 官方现代入口、原作/移植/重制关系 |
| 经典再发现 | 不靠任务箭头的引导：选一段经典流程做场景拆解 | 画面证据、流程条件与解释，不推断设计师心理 |
| 经典再发现 | 大镖客中的某一个环境反应，怎样增强世界可信度 | 原始演示或本人复现；避免“每个NPC”绝对断言 |
| 经典再发现 | 星露谷的一条已知小彩蛋，为什么仍让玩家愿意分享 | 可确认机制、来源、读者观察，不制造“无人发现” |
| 作品背后 | 宫崎英高某段旧访谈里的取舍，如何对应一个实际场景 | 原访谈日期/原文、作品角色、场景证据 |
| 作品背后 | 一家工作室不同作品的设计共性，是否真的存在 | 至少两个具体作品例子与反例，不做天才神话 |
| 作品背后 | 某奖项中一组工作室的作品回顾 | 官方奖项记录、时期、归属规则；不声称实力总榜 |
| 作品背后 | 一次开发限制如何改变最终玩法 | 开发日志/演讲及作品内容，不虚构内幕 |

题材池首发建议先人工确认10–20个游戏／系列与少量制作人／工作室。按本人熟悉度和资料完整度扩张；不是AI从名气榜随机抓一百个名字。

## 21. 开发交付与停止条件

交付物：迁移说明、可运行本地编辑台、三栏目配置、双选题池、来源/主张/素材模型、可复算选购流程、待审稿导出、发布记录、指标复盘、测试报告。

北极星：**每周实际采用的合格简报数，以及为一篇可信帖子花掉的人工时间。** 阅读、收藏、关注等结果在本人发布后观察；不以“抓了几百条、生成几十篇”作为成功。

当一个功能不能解释如何提高选题/核验/编辑效率时，暂缓。尤其不要再次加入SEO评分、更多无关平台的热度分、复杂自动Agent循环或为凑篇数生成内容。

最终关系保持清楚：

> **盒友编辑台：今天值得给玩家看什么，依据是什么。**
> **游戏词雷达：下一个网站／页面值得研究什么，需求证据是什么。**
